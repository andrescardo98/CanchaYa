## Aspectos generales

Aspectos generales y transversales — CanchaYa

Artefacto de apoyo 1.1.9.5. Reglas que aplican a todas las historias de usuario, para no repetirlas en cada una. Cada hoja HU del Tallaje enlaza a este documento en la fila «Aspectos generales». Todos los aspectos están aprobados. Corte: 26-oct-2026.

| Código | Categoría | Aspecto | Regla | Origen | Estado | Observación |
|---|---|---|---|---|---|---|
| AG-01 | Validación y formularios | Validación en el cliente y en el servidor | El cliente valida cada dato para guiar al usuario, pero el servidor vuelve a validar todo con las políticas del modelo de dominio enriquecido y es el que decide. Ninguna regla de negocio depende solo de la interfaz. | Tallaje (DoD-4); Project Canvas (seguridad) | Definido |  |
| AG-02 | Validación y formularios | Validación al perder el foco | Cuando el usuario sale de un campo, ese campo se valida según su requisito de información. Si el dato es correcto no se muestra nada; si no, se muestra junto al campo el mensaje que corresponde (ERR-GEN-01 obligatoriedad, 02 formato, 03 longitud, 04 rango). | Criterios de aceptación de HU1, HU3, HU5, HU6, HU8 y HU15 | Definido |  |
| AG-03 | Validación y formularios | Validación al ejecutar la acción | Al ejecutar la acción (registrar, guardar, reservar…), si algún dato incumple una regla no se persiste nada y se muestran todos los mensajes de error, indicando el problema y cómo remediarlo. | Criterios de aceptación de las HU con formulario | Definido |  |
| AG-04 | Validación y formularios | Formulario después de la acción | Si un registro termina bien, el formulario se limpia y se muestra el mensaje de éxito. Si una modificación termina bien, el formulario muestra los datos actualizados. Si hay error, el formulario conserva lo que el usuario escribió, excepto los campos de contraseña. | Criterios de aceptación de HU1, HU3, HU5, HU6, HU7 y HU15; aprobado por el usuario el 26-oct-2026 | Definido |  |
| AG-05 | Validación y formularios | Comparación de textos únicos | Para detectar duplicados (correo electrónico, nombre de cancha en un escenario, código de tipo de cancha) se compara el contenido sin distinguir mayúsculas de minúsculas. Al modificar, se excluye el propio registro. | Aclaraciones de HU1, HU3, HU6 y HU9; plantilla de HU del curso | Definido | El código de tipo de cancha además solo admite mayúsculas y dígitos (enriquecido). |
| AG-06 | Validación y formularios | Espacios sobrantes | Antes de validar y guardar un texto se eliminan los espacios al inicio y al final. Un campo que solo tiene espacios se considera vacío (ERR-GEN-01). | Aprobado por el usuario el 26-oct-2026 (práctica del proyecto de Semestre 2: UtilTexto.aplicarTrim) | Definido |  |
| AG-07 | Mensajes | Origen de los mensajes | Todo mensaje que ve el usuario sale del catálogo de mensajes, por su código. No se escriben textos sueltos en el código fuente. Los valores de negocio de los textos salen del catálogo de parámetros. | Tallaje (texto provisional de aspectos generales); catálogo de mensajes | Definido |  |
| AG-08 | Mensajes | Confirmación de acciones que no se pueden deshacer | Eliminar (horario, bloqueo, tipo de cancha, encargado), cancelar una reserva y marcar una inasistencia piden antes un mensaje de confirmación (CNF). Si el usuario cancela la confirmación, nada cambia. | Criterios de aceptación de HU12, HU17, HU24, HU31, HU33 y HU36 | Definido | La cancelación por fuerza mayor (HU32) no usa CNF: exige escribir la justificación. |
| AG-09 | Mensajes | Consultas sin resultados | Una lista o búsqueda vacía no se muestra en blanco: muestra un mensaje informativo (INF) que explica por qué no hay datos y, si aplica, qué puede hacer el usuario. | Criterios de aceptación de HU14, HU18, HU20, HU23, HU35 y HU38 | Definido |  |
| AG-10 | Mensajes | Errores inesperados | Ante cualquier error no controlado se muestra ERR-GEN-07 y el detalle técnico se registra solo en el log. El usuario nunca ve trazas, nombres de clases ni mensajes de la base de datos. | Catálogo de mensajes (ERR-GEN-07) | Definido |  |
| AG-11 | Seguridad | Sesión | Buscar canchas, ver la ficha de un escenario y consultar disponibilidad no requieren sesión. Todo lo demás exige sesión iniciada con token JWT; sin sesión o con la sesión vencida se muestra ERR-GEN-05 y se lleva al usuario al inicio de sesión. | D11; D17; HU2; HU4 | Definido | La vigencia del token es PAR-USU-09: 60 minutos, sin renovación (D37). |
| AG-12 | Seguridad | Permisos en el servidor | El servidor valida en cada operación el rol del token y, cuando aplica, la propiedad: propietario del escenario o encargado asignado. Ocultar un botón en la interfaz no reemplaza esta validación. | Project Canvas; D02; D03; D07 | Definido |  |
| AG-13 | Seguridad | Contraseñas | La contraseña se escribe en un campo oculto, se guarda solo como hash bcrypt y nunca se muestra, se devuelve en una respuesta ni se escribe en el log. | Modelo enriquecido (Usuario.contrasenaHash); aclaración de HU1 | Definido |  |
| AG-14 | Seguridad | Datos no visibles | Los atributos que el requisito de información marca como no visibles (identificadores, hash de la contraseña, estados internos, fechas de registro) no se muestran en pantalla. Cada HU lista los suyos en su conversación. | Plantilla de HU del curso; aclaraciones de HU1 y HU5 | Definido |  |
| AG-15 | Seguridad | Datos sensibles | El número de documento y el celular del usuario son datos sensibles. El celular del jugador solo lo ven el propietario y los encargados del escenario donde reservó (agenda y correo de nueva reserva). El celular personal del administrador nunca se muestra en la ficha pública: allí va el teléfono de contacto del escenario. | Modelo enriquecido (¿Sensible?); aclaraciones de HU19 y HU29; COR-RES-02 | Definido | Tratamiento de datos según la Ley 1581 de 2012. |
| AG-16 | Datos y formatos | Identificadores | Todo registro tiene un identificador UUID que genera el servidor. El usuario nunca lo escribe ni lo ve. | Modelo enriquecido; convención del modelo de dominio | Definido |  |
| AG-17 | Datos y formatos | Zona horaria | Todas las fechas, horas y plazos se calculan con la hora del servidor en America/Bogota (UTC-5). No se usa la hora del dispositivo del usuario. | D27; PAR-GEN-01 | Definido |  |
| AG-18 | Datos y formatos | Formato de fechas y horas | Las fechas se muestran como dd/mm/aaaa y las horas como hh:mm. Las fechas de registro, cuando se muestran, como dd/mm/aaaa hh:mm. | Modelo enriquecido (formatos de los atributos) | Definido |  |
| AG-19 | Datos y formatos | Formato de precios | Los precios están en pesos colombianos y se muestran con signo y separador de miles, sin decimales (por ejemplo, $ 80.000). Internamente se guardan con 2 decimales. | Modelo enriquecido (precisión 2); aprobado por el usuario el 26-oct-2026 | Definido |  |
| AG-20 | Datos y formatos | Calificación promedio | La calificación promedio de un escenario se calcula al consultar, se muestra con un decimal y no aparece si el escenario aún no tiene reseñas. | D05; modelo enriquecido; HU19 | Definido |  |
| AG-21 | Interfaz | Diseño adaptable | Todas las pantallas funcionan en celular y en computador (diseño responsivo); no hay aplicación móvil nativa. | Project Canvas | Definido |  |
| AG-22 | Interfaz | Idioma | La interfaz, los mensajes y los correos están en español de Colombia. | Aprobado por el usuario el 26-oct-2026 | Definido |  |
| AG-23 | Integraciones | Correos electrónicos | Solo se envían los correos del catálogo (COR-ESC-01 y COR-RES-01 a 06). Si un envío falla, la operación no se revierte, se registra el error (ERR-GEN-08) y no se reintenta. | D15; D19; PAR-GEN-02 | Definido |  |
